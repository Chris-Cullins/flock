# Flock — Architecture Document

*Coordinated version control for the agentic era.*

**Project:** Flock
**CLI command:** `fl`
**Mascot:** The Goose

## Executive Summary

Flock is a next-generation version control system designed from the ground up for a world where AI agents are first-class participants in software development. The system preserves the brilliant foundations of git (content-addressable storage, Merkle trees, distributed operation) while fundamentally rethinking the data model, merge strategy, and workflow primitives for high-frequency, multi-agent, semantically-aware development.

## How Git Works Under the Hood (A Primer)

Before diving into the new architecture, it helps to understand what git actually does at a mechanical level, since Flock builds on some of these ideas and deliberately departs from others.

### Git's Object Model

At its core, git is a content-addressable filesystem. Everything is stored as one of four object types, each identified by a SHA-1 hash of its contents:

**Blobs** store file contents. When you add a file, git compresses the entire file content and stores it as a blob. The key insight: two files with identical content share the same blob, regardless of filename or location. But if even one byte changes, it's an entirely new blob — git stores the whole new version, not a delta.

**Trees** represent directories. A tree object contains a list of entries, where each entry points to either a blob (file) or another tree (subdirectory), along with the filename and file mode. This is how git maps the flat blob storage back to a directory structure.

**Commits** tie everything together. A commit points to a tree (the root of the project at that moment), one or more parent commits (creating the history graph), and metadata (author, committer, message, timestamp). A commit is a complete snapshot of the entire project — not a diff, not a delta, but a full picture.

**Tags** are named pointers to commits (usually for releases).

So when you run `git commit`, git:

1. Takes every file in your staging area and stores each as a blob
2. Builds tree objects representing your directory structure
3. Creates a commit object pointing to the root tree, your previous commit, and your metadata
4. Updates the branch ref (e.g., `refs/heads/main`) to point to the new commit

### How Git Stores Data Efficiently

You might think storing complete file snapshots on every commit would be wildly wasteful. Git handles this in two ways. First, identical content deduplicates automatically since the same content always produces the same hash. Second, git periodically runs "garbage collection" which packs loose objects into packfiles. Packfiles use delta compression — git finds similar objects and stores one as a base plus deltas to reconstruct the others. But this is purely a storage optimization; the logical model is always complete snapshots.

### How Git Merges Work

This is where git's limitations become clear in an agentic world. Git's merge algorithm is purely text-based. When merging two branches, git:

1. Finds the common ancestor commit (merge base)
2. Computes a text diff from the merge base to each branch tip
3. Attempts to apply both sets of text changes to the merge base
4. If the same lines were modified differently, it declares a conflict

Git has zero understanding of what the code means. It doesn't know if two changes to the same file are semantically independent. It doesn't know if a change in file A breaks an interface used in file B. It just sees lines of text.

### Why Git Breaks Down for Agents

Several specific problems emerge:

**Commit granularity mismatch.** An agent exploring a solution might make hundreds of meaningful state changes per minute. Each `git commit` has overhead (hashing, tree construction, ref updates), and the resulting history is either too noisy (commit per micro-change) or too coarse (one big commit that loses the exploration path).

**Branch overhead.** Git branches are lightweight (just a ref pointer), but actually using branches — checkout, merge, rebase — involves full working tree operations. An agent that wants to explore 10 approaches in parallel needs 10 working copies or complex stash/worktree management.

**Text-based merging.** When multiple agents work on the same codebase, text-based merging produces false conflicts (semantically independent changes that touch the same lines) and misses real conflicts (semantically breaking changes in different files). This is git's deepest limitation.

**No provenance model.** Git tracks author and committer. There's no built-in concept of "this change was directed by developer X, generated by agent Y, reviewed by developer Z, and tested by agent W." The rich causal chain that matters in agentic workflows is lost.

## Flock Architecture Overview

Flock is structured as a layered system. Each layer can operate independently, with higher layers adding intelligence:

```
┌─────────────────────────────────────────────┐
│            Developer Experience              │  CLI, editor integration, visualization
├─────────────────────────────────────────────┤
│            Collaboration Layer              │  Presence, subscriptions, gating
├─────────────────────────────────────────────┤
│            Agent Workflow Layer              │  Explorations, sessions, sandboxes
├─────────────────────────────────────────────┤
│            Semantic Layer                    │  AST diff, intent tracking, smart merge
├─────────────────────────────────────────────┤
│            Core Storage Engine               │  Event log, snapshots, content store
└─────────────────────────────────────────────┘
```

The critical design principle: **every layer degrades gracefully.** If the semantic layer can't parse a file, it falls back to text-level operations. If the agent workflow layer isn't being used, the system behaves like a (better) traditional VCS. You never lose data or functionality because a higher layer fails.

## Lessons from Jujutsu (jj): What to Adopt and Where to Go Further

Jujutsu (jj) is the most interesting VCS to emerge since git. It's being actively developed at Google, it's Git-compatible, and it has built a passionate user base. Before designing Flock, we should understand what jj got right, what we should adopt directly, and where we need to go beyond it for the agentic world.

### What jj Got Right (Adopt Directly)

**1. Working copy as a commit.** In git, your working directory is a weird limbo state — not yet a commit, managed by a separate set of commands (`git add`, `git stash`, the staging area). jj eliminated this entirely. Your working copy *is* a commit, automatically snapshotted on every operation. This means there's only one kind of object in the system (commits), and every command that works on commits also works on your current work. No staging area, no stash, no special cases.

**Flock adopts this fully.** In our event log model, the working state is just the latest event in the workspace's timeline. There's never a "not yet tracked" state. This is even more critical for agents — an agent shouldn't have to `add` and `commit` as separate steps. Everything it does is automatically captured.

**2. First-class conflicts.** This is arguably jj's biggest innovation. In git, a conflict is an error that halts everything — you're stuck in a broken state until you resolve it, and you can't do anything else. In jj, a conflict is just data stored in the commit. Operations like rebase succeed even when they produce conflicts. You can commit conflicted state, switch to other work, come back later, and resolve at your leisure. Conflicts don't cascade into nested markers when rebased further — jj stores the logical conflict structure, not textual markers.

**Flock adopts this fully and extends it.** Our semantic layer goes further by classifying conflicts (is this a style conflict? a logic conflict? a breaking API change?) and auto-resolving the ones that aren't real conflicts at the semantic level. But the foundation — conflicts as first-class data, not errors — comes directly from jj.

**3. Operation log and undo.** jj records every operation you perform on the repository (commits, rebases, merges, everything) in a separate operation log. You can `jj undo` any operation, `jj redo` it, or `jj op restore` to jump back to any point in the operation history. This is an incredible safety net — you literally cannot lose work because every state is recoverable.

**Flock adopts this directly as the event log.** Our append-only event log is philosophically the same thing as jj's operation log, but taken further: we record not just high-level operations but individual file writes, giving much finer granularity. The undo system described in our Requirement 2 is a superset of jj's undo — we support per-file undo, time-based undo, and event-level undo, not just operation-level.

**4. Automatic rebasing of descendants.** When you edit a commit in the middle of your history, jj automatically rebases all descendant commits onto your edited version. In git, this requires a manual interactive rebase, and if things go wrong, you're in trouble. In jj, it just happens — you edit the commit, and descendants update. If conflicts appear, they're recorded (see above) but don't block you.

**Flock adopts this, and it's essential for the multi-agent case.** When Agent A's work gets merged and changes the main timeline, the continuous rebase system in our collaboration layer does the same thing — automatically rebasing active workspaces and recording any resulting conflicts without blocking agents.

**5. Revsets (the query language).** jj borrowed Mercurial's revset concept — a powerful expression language for selecting sets of commits. Instead of memorizing git's inconsistent syntax, you write things like `jj log -r 'author(alice) & file(*.py)'` or `jj log -r 'main..@'`. It's composable, readable, and powerful.

**Flock adopts revsets and extends them with semantic queries.** Our query language adds intent-based and semantic filters on top of the structural revset model: `fl log -r 'intent(bugfix) & affects(PaymentProcessor)'`. The revset foundation is proven — no need to reinvent it.

**6. Anonymous branches (change IDs vs. commit IDs).** In git, you must name a branch before doing work. In jj, every change gets a stable, randomly-generated change ID that persists even as the underlying commit hash changes due to rebasing or amending. Branches (called "bookmarks" in jj) exist but are optional — you can do substantial work without ever naming a branch.

**Flock adopts the stable change ID concept.** Our explorations have UUIDs that persist through any transformation. Named branches exist for publishing to remotes and for human coordination, but day-to-day agent work is identified by exploration ID, not branch name. Agents shouldn't have to make up branch names.

**7. The `absorb` command.** `jj absorb` automatically distributes changes from your working copy into the correct ancestor commits — it figures out which commit last touched each line and moves the fix there. This is incredibly useful for stacked-diff workflows where you're maintaining multiple logical changes.

**Flock adopts this concept in the semantic merge layer.** When an agent is working across multiple areas of the codebase, the system can automatically attribute changes to the correct semantic scope and route them accordingly. Combined with our AST-level understanding, absorb becomes even smarter — routing changes by semantic unit (method, class), not just by line-level blame.

### Where jj Falls Short for Agents (Where Flock Goes Further)

**1. Still text-based merging.** jj's conflict handling is brilliant in how it stores and manages conflicts, but the actual merge algorithm is still fundamentally text-based (line-level diff and merge). It doesn't understand code structure. Two agents reformatting the same file still creates a conflict. A method signature change in one file that breaks callers in another file still merges cleanly. Flock's semantic layer addresses this directly.

**2. No agent-specific workflow primitives.** jj is designed for human developers. It has no concept of agent sessions, explorations with TTLs, workspace isolation with resource limits, or provenance chains. You could use jj's workspaces and branches for agent work, but you'd be fighting the tool — there's no built-in support for "this agent should only see these files" or "auto-prune explorations older than 1 hour."

**3. No coordination protocol.** jj handles concurrent operations safely (one of its explicit design goals — you can even run it from Dropbox), but it doesn't have proactive coordination. There's no way to say "I'm working on this area, other agents should avoid it" or "notify me when someone changes this interface." For 10 agents working 24/7, reactive conflict handling isn't enough — you need proactive coordination.

**4. No semantic code review.** jj's diff output is better than git's (it shows cleaner conflict markers with diff-from-base), but it's still a text diff. There's no "here are the 5 semantic changes in this commit" view. For reviewing agent-generated code at scale, text diffs don't cut it.

**5. Single-machine focus.** jj is designed as a local tool that syncs to git remotes. It doesn't have a server component for things like real-time presence, centralized semantic indexing, or server-side AST computation. For enterprise-scale agent coordination, some server-side intelligence is needed.

### Summary: jj Is Our Foundation, Not Our Ceiling

The mental model shift that jj pioneered — working copy as a commit, first-class conflicts, operation log with undo, automatic rebasing, revsets — is the right foundation. Flock should feel like jj to a human developer using it for everyday work. The additions Flock makes (semantic layer, agent workflows, coordination protocol, high-level code review) are layers on top of that foundation, not replacements for it.

If a developer already knows jj, Flock should feel like "jj, but it also understands my code structure and works natively with AI agents."

## Key Functional Requirements

Before diving into each layer, here are the three core use-case requirements that drive the architecture. Everything in the system is designed to make these experiences great.

### Requirement 1: High-Level Code Review (Not Line-Level Diffs)

**The problem today:** A developer opens a pull request in GitHub and sees "+4,237 lines, -1,892 lines" across 47 files. Most of those changes might be a single meaningful refactor — but the reviewer has to scroll through thousands of green and red lines to understand what actually happened. This doesn't scale when agents are making changes, because agents produce large, correct-but-verbose diffs at high volume.

**What Flock does instead:** Code review operates at the *semantic change* level by default, not the line level. When you review a set of changes, you see something like:

```
Review: exploration "optimize-payment-processing" by agent:copilot
────────────────────────────────────────────────────────────────────

Summary: Refactored PaymentProcessor to extract validation into a
         separate service. Added currency conversion support.

Changes (5 semantic units):

  1. [New Class]      CurrencyConverter
     └─ src/Services/CurrencyConverter.cs
     └─ 3 public methods, implements ICurrencyConverter

  2. [New Interface]   ICurrencyConverter
     └─ src/Interfaces/ICurrencyConverter.cs

  3. [Extracted Method] PaymentProcessor.ValidatePayment()
     └─ Moved from PaymentProcessor.Process() lines 47-93
     └─ Now in PaymentValidator.Validate()
     └─ Original call site updated to delegate

  4. [Signature Change] PaymentProcessor.Process()
     └─ Added parameter: string currency (default: "USD")
     └─ ⚠ 12 callers affected (all updated)

  5. [Style Only]      Reformatted 8 files (no semantic change)
     └─ Auto-approved by policy
```

Each of those items is expandable. Click into "Extracted Method" and you see the actual code — but you're choosing to look at the implementation of a *specific semantic change*, not scrolling through raw diffs hoping to find the meaningful parts.

**How it works architecturally:**

The semantic layer's AST diffing engine computes the change set between the base and the proposed changes. Instead of producing line-level diffs, it produces a list of `SemanticChange` objects, each of which describes a structural modification:

```
SemanticChange {
    kind:         Added | Removed | Modified | Moved | Renamed | StyleOnly
    target:       Symbol (class, method, interface, field, etc.)
    scope:        Local | CrossFile | CrossModule
    impact:       [Symbol] (downstream consumers affected)
    risk:         Low | Medium | High (based on scope and impact)
    reviewable:   bool (false for auto-approved style changes)
    drill_down:   DiffView (the actual code diff for this specific change)
}
```

The review UI groups these by risk level — high-impact changes (interface modifications, breaking changes) surface first, style-only changes are collapsed or auto-approved by policy, and the reviewer can drill into any individual change to see the actual code.

**What this means for real workflows:**

- A reviewer can approve 5 semantic changes instead of reading 4,000 lines of diff
- Style-only changes (reformatting, import reordering) are automatically separated out
- Breaking changes are flagged with the full list of affected callers
- "Move method" and "rename" operations are shown as what they are, not as massive delete+add blocks
- Review policies can be defined at the semantic level: "auto-approve all StyleOnly changes, require 2 reviewers for any SignatureChange"

### Requirement 2: Instant Agent Undo (Without Rewriting Files)

**The problem today:** An agent writes 15 files, and on the last one it accidentally uses tabs instead of spaces (or introduces a bug, or goes down the wrong path). In git, the options are bad: `git checkout` the files back and redo the work, manually fix each file, or hope you committed before the mistake. The agent itself often resorts to reading each file back and rewriting it, which is slow, token-expensive, and error-prone.

**What Flock does instead:** Every single edit an agent makes is an event in the log. Undo is just "rewind the event log to before that edit." No file rewriting, no re-reading content, no hoping you remembered to commit. It's instant because nothing is actually being undone — you're just moving a pointer.

Here's the key insight: in the event log model, the current state of a file is defined by replaying events up to a certain point. "Undo the last edit" means "set the current pointer to the event before the last edit." The blocks that made up the file before the bad edit are still in the content store (they're never deleted). So reconstructing the pre-edit state is just reassembling existing blocks — no I/O to rewrite anything.

```
Event timeline for an agent's workspace:

  ... → e47: wrote FileA.cs    → e48: wrote FileB.cs
      → e49: wrote FileC.cs    → e50: wrote FileD.cs (tabs!)
                                       ↑
                                  current pointer

After undo:

  ... → e47: wrote FileA.cs    → e48: wrote FileB.cs
      → e49: wrote FileC.cs    → e50: wrote FileD.cs (tabs!)
                          ↑
                     current pointer (FileD.cs reverts to pre-e50 state)

Agent fixes and continues:

  ... → e49: wrote FileC.cs    → e51: wrote FileD.cs (spaces!)
                                       ↑
                                  current pointer
```

Event e50 isn't deleted — it's still in the log for audit purposes. But the workspace's current state no longer includes it. This is exactly like hitting undo in a text editor, but at the repository level.

**Granularity options:**

- `fl undo` — undo the last event (single file write)
- `fl undo --n 3` — undo the last 3 events
- `fl undo --to e47` — rewind to a specific event
- `fl undo --file src/FileD.cs` — undo only changes to a specific file (keeping other changes)
- `fl undo --since 5m` — undo everything from the last 5 minutes

**Performance characteristics:**

Undo is O(1) — it's just moving a pointer. There's no diffing, no file I/O, no recomputation. This is critical for the agent use case. An agent that makes a mistake shouldn't burn tokens or time recovering; it should be able to undo instantly and continue working. The copy-on-write snapshot model means the "before" state is always available without any reconstruction cost.

**Per-file undo (the hard part):**

The tricky case is "undo just the change to FileD.cs but keep the changes to FileA, FileB, and FileC." This requires the system to reconstruct the state of FileD.cs at a previous event while keeping the rest of the workspace at the current event. The block-level content store makes this possible — since each file is tracked as an independent sequence of block references, you can "rewind" one file's block list without affecting others. The system creates a new event that says "FileD.cs now points to its block list as of event e49" while leaving everything else as-is.

### Requirement 3: 10 Agents, Zero Merge Hell

**The problem today:** Even with 2-3 developers working on the same codebase, git merge conflicts are a constant friction. Now scale that to 10 AI agents working 24/7, each generating changes at machine speed. The traditional git workflow of branch → work → pull → resolve conflicts → push becomes a nightmare. Agents spend more time dealing with merge conflicts than doing actual work. The `stash → fetch → pull → pop stash → resolve → push` dance is a massive bottleneck.

**What Flock does instead:** The architecture eliminates most merge conflicts at the source through three mechanisms working together: workspace isolation, semantic auto-merge, and a coordination protocol.

**Mechanism 1: Isolated Workspaces (Agents Never Step on Each Other)**

Each agent operates in its own isolated workspace — a lightweight, copy-on-write view of the repository. There is no shared working directory. There is no `git pull` that disrupts your in-progress work. Each agent sees a stable snapshot of the repo and works against that snapshot without interruption.

```
Main timeline:  ───●───●───●───●───●───●──→

Agent A workspace: ──┐ (forked at ●)
                     ├── works in isolation
                     └── merges back when done

Agent B workspace: ─────┐ (forked at ●)
                        ├── works in isolation
                        └── merges back when done

Agent C workspace: ────────┐ (forked at ●)
                           ├── works in isolation
                           └── merges back when done

(10 agents, all working simultaneously, none blocking each other)
```

The agent never needs to stash, fetch, or pull. It works against its snapshot. When it's done, it merges — and because the merge happens at the semantic level (not line level), most "conflicts" resolve automatically.

**Mechanism 2: Semantic Auto-Merge (Most "Conflicts" Aren't Real)**

When Agent A and Agent B both finish their work and merge back, Flock doesn't just compare lines of text. It compares semantic changes. This eliminates entire categories of false conflicts:

| Scenario | Git Result | Flock Result |
|----------|-----------|-------------|
| A adds method to class, B reformats same class | CONFLICT | Auto-merge (independent changes) |
| A modifies function body, B adds new function to same file | CONFLICT (adjacent lines) | Auto-merge (different semantic units) |
| A renames variable throughout file, B adds new code to same file | CONFLICT | Auto-merge (rename doesn't affect new code) |
| A and B both modify the same function body | CONFLICT | TRUE CONFLICT (flagged for review) |
| A changes method signature, B calls that method in another file | Clean merge (!) | TRUE CONFLICT (caught across files!) |

In practice, with 10 agents working on a large codebase, the vast majority of concurrent changes are to *different semantic units* that happen to be in the same files. Semantic merge resolves these automatically. The remaining true conflicts are flagged with full context about why they conflict, not just "lines 47-53 differ."

**Mechanism 3: Coordination Protocol (Avoid Conflicts Before They Happen)**

Beyond just handling conflicts well, Flock actively reduces them through coordination:

**Region locking (optional):** Before an agent starts work on a module, it can acquire a soft lock:

```
fl lock acquire --scope src/Services/PaymentProcessor.cs --agent agent-A --ttl 30m
```

Other agents can see the lock and choose to work elsewhere, or override it if needed. Locks are advisory (not blocking) and time-limited (auto-release after TTL). This isn't like pessimistic file locking from SVN — it's a coordination hint that agents use to avoid doing duplicate work.

**Semantic region partitioning:** The system can automatically partition the codebase into non-overlapping semantic regions and assign agents to regions:

```
Agent A: owns src/Services/Payment*        (payment domain)
Agent B: owns src/Services/Inventory*      (inventory domain)
Agent C: owns src/Api/Controllers/*        (API layer)
Agent D: owns tests/**                     (test suite)
```

Changes within your region never conflict with other agents. Changes that cross region boundaries trigger the coordination protocol (notify affected region owners, queue for semantic merge).

**Continuous rebase (background sync):** Instead of letting an agent's workspace drift far from main (creating large, conflict-prone merges at the end), Flock can optionally rebase an agent's workspace against main in the background:

```
Workspace config:
    auto_rebase: true
    rebase_interval: 5m
    rebase_strategy: semantic  (only rebase if changes don't conflict)
    on_conflict: pause_and_notify  (don't force-resolve, alert the agent)
```

Every 5 minutes, the system checks if main has moved ahead of the agent's workspace base. If so, it attempts a semantic rebase. If there are no conflicts, the agent's workspace is silently updated — it doesn't even notice. If there's a conflict with the agent's in-progress work, the agent is notified and can decide how to handle it.

**The net effect on workflow:**

In git with 10 agents, the workflow is:
```
branch → work → stash → fetch → pull → pop stash → resolve conflicts
→ test → push → pray nobody pushed while you were testing → repeat
```

In Flock with 10 agents, the workflow is:
```
create workspace → work → finish → merge (almost always auto-resolves)
```

No stashing. No fetching. No pull conflicts. No push races. The system handles isolation, synchronization, and conflict resolution automatically, and the rare true conflicts are presented with full semantic context so they can be resolved quickly and correctly.

This is the foundation. It replaces git's object model with something optimized for high-frequency, fine-grained changes while preserving content-addressable integrity.

### The Event Log

Instead of git's discrete commit snapshots, the fundamental data structure is an append-only event log. The idea is simple: every single change to the repository gets recorded as an immutable entry in a sequential log, like a ledger that you can only add to, never erase. Think of it like a write-ahead log in a database — the system writes down what it's about to do before it does it, so it always has a complete record.

Every mutation to the repository is recorded as an event:

```
Event {
    id:          UUID
    timestamp:   u64 (nanosecond precision)
    actor:       ActorID (human, agent, or system)
    parent:      EventID (previous event in this timeline)
    kind:        EventKind
    payload:     bytes (compressed)
    signature:   bytes (ed25519)
}

EventKind:
    | FileWrite    { path, content_hash, block_ranges }
    | FileDelete   { path }
    | FileRename   { old_path, new_path }
    | Checkpoint   { label, metadata }
    | BranchCreate { name, base_event }
    | BranchMerge  { source, target, resolution }
    | IntentTag    { event_range, intent_description }
    | Exploration  { action: Start | Commit | Abandon }
    | Undo         { target_event, scope: All | File(path) }
    | LockAcquire  { scope, actor, ttl }
    | LockRelease  { scope, actor }
    | TaskCreate   { task_id, title, priority, kind, dependencies }
    | TaskUpdate   { task_id, field_changes }
    | TaskLink     { task_id, event_id }
```

**Commits are just checkpoint events.** A "commit" in Flock is simply a `Checkpoint` event with a label and metadata. The event log captures everything in between. This means you get full granularity when you want it (agent debugging, audit trails) and clean history when you don't (just look at checkpoints).

**Why an event log?** Several reasons:

- High-frequency writes are cheap — just append
- You never lose history — events are immutable
- Branching is trivial — a branch is just a new event with a different parent pointer
- Replication is simple — just ship events
- You can reconstruct any point-in-time state by replaying events

### Block-Level Content Store

Git stores content at the file level. Flock stores content at the block level. A "block" is a configurable chunk of a file — it could be a function, a class, a fixed-size byte range, or a language-aware semantic unit.

```
ContentStore:
    block_hash → compressed_block_data

FileIndex:
    (path, event_id) → [BlockRef, BlockRef, ...]

BlockRef {
    hash:     ContentHash
    offset:   u64
    length:   u64
    kind:     Raw | ASTNode(node_type)
}
```

**Why block-level?** When an agent modifies a single function in a large file, git stores the entire new file as a new blob. Flock only stores the changed blocks. In a monorepo with thousands of large files being touched by multiple agents, this dramatically reduces storage requirements.

Content is still addressed by hash (we use BLAKE3 instead of SHA-1 for speed and security). Identical blocks still deduplicate. The integrity guarantees are the same as git's, just at a finer granularity.

### Snapshots via Merkle Tree

At any checkpoint event, Flock can construct a Merkle tree of the entire repository state — just like git's tree objects. This provides:

- O(1) equality checks between any two points in time (compare root hashes)
- Efficient synchronization (only transfer subtrees that differ)
- Cryptographic integrity verification of the entire repo

The difference from git is that the leaf nodes of the tree are block references, not file blob references. This makes the tree more granular and the diff operations more efficient.

```
                     [root hash]
                    /            \
             [src/ hash]      [tests/ hash]
              /        \           |
    [api/ hash]  [core/ hash]  [test files...]
        |             |
  [file blocks]  [file blocks]
```

### Copy-on-Write Snapshots

When an agent wants to explore an approach, Flock creates a copy-on-write (CoW) snapshot. This is similar to how modern filesystems (ZFS, btrfs) handle snapshots:

- The snapshot starts as a zero-cost pointer to the current state
- Only blocks that change get new storage
- Unchanged blocks are shared with the original

This means spinning up a new exploration costs essentially nothing — no copying files, no creating working directories, no checkout operations. An agent can fork 50 explorations and the only storage cost is the blocks that actually differ between them.

### Storage Tiers

For enterprise scale, the content store supports tiered storage:

- **Hot tier** (local SSD): Recent blocks, active explorations, frequently accessed files
- **Warm tier** (networked storage): Older blocks, completed explorations not yet pruned
- **Cool tier** (object storage like S3): Archived history, rarely accessed content

Block promotion and demotion happens automatically based on access patterns. A block that hasn't been read in 90 days migrates to cool storage. When accessed, it's transparently fetched and promoted.

## Layer 2: Semantic Layer

This is where Flock fundamentally departs from git. The semantic layer understands code structure, not just text.

### AST-Aware Diffing

Instead of computing line-based text diffs, Flock parses source files into Abstract Syntax Trees and diffs at the tree level. A tree diff can distinguish:

- A function was renamed (git sees every line in the function as deleted and re-added)
- A parameter was added to a method signature (git sees one changed line; Flock sees a structural change to an interface)
- Code was reformatted with no semantic change (git sees dozens of changed lines; Flock sees zero meaningful changes)
- An `if` block was wrapped around existing code (git sees indentation changes on every line; Flock sees a single structural insertion)

The diffing algorithm is based on tree edit distance computation. Given two ASTs, find the minimum set of tree operations (insert node, delete node, move node, update node value) that transforms one into the other. This is more computationally expensive than line diff, but produces dramatically more meaningful results.

### Language Analyzers

AST diffing requires language-specific parsers. Flock uses a plugin architecture for language support:

```
LanguageAnalyzer trait:
    parse(source: bytes) → AST
    diff(old: AST, new: AST) → [SemanticChange]
    merge(base: AST, left: [SemanticChange], right: [SemanticChange]) → MergeResult
    extract_symbols(ast: AST) → [Symbol]
    check_compatibility(old_symbols: [Symbol], new_symbols: [Symbol]) → [BreakingChange]
```

Each analyzer ships as a plugin. The system starts with C# support (given the enterprise .NET context) and expands from there. For unsupported languages, the semantic layer falls back to text-based operations — you never lose functionality, just intelligence.

The parsers use tree-sitter under the hood — it's fast, incremental (can re-parse only changed portions), handles syntax errors gracefully, and supports dozens of languages. Flock wraps tree-sitter with higher-level semantic understanding specific to each language.

### Semantic Merge Engine

This is the core innovation. Instead of merging text, Flock merges semantic changes. The algorithm:

1. Parse the base version, left branch, and right branch into ASTs
2. Compute semantic change sets: base→left and base→right
3. Classify each change by what it affects (function body, interface signature, import, type definition, etc.)
4. Check for true conflicts: two changes that affect the same semantic unit in incompatible ways
5. Apply non-conflicting changes automatically
6. Present true conflicts with full semantic context

**Example of a false conflict git would flag that Flock resolves automatically:**

Left branch adds a new method to a class. Right branch reformats the same class. Git sees overlapping line changes and declares a conflict. Flock sees "add method" and "whitespace-only change" and applies both cleanly.

**Example of a real conflict git would miss that Flock catches:**

Left branch changes a method signature from `Calculate(decimal amount)` to `Calculate(decimal amount, string currency)`. Right branch, in a different file, calls `Calculate(total)` without the new parameter. Git merges cleanly (different files, no text conflict). Flock flags the breaking interface change.

### Intent Tracking

Every change in Flock can be tagged with intent — a structured description of why the change was made:

```
Intent {
    id:          UUID
    description: string (human-readable)
    category:    Refactor | Feature | Bugfix | Optimization | Style | ...
    scope:       [FilePath | ModulePath | Symbol]
    related:     [IntentID] (parent intents, related changes)
    confidence:  f64 (for AI-generated intents)
}
```

When an agent makes changes, it attaches intents automatically ("refactoring payment processing to extract validation logic"). When a human makes changes, the commit message is parsed into structured intent (with AI assistance).

Intents make merge decisions smarter. Two changes to the same file with unrelated intents (one fixing a bug, one adding a feature to a different function) can merge with high confidence. Two changes with related intents (both modifying the same validation logic) need careful review.

### Dependency Graph

Flock maintains a live dependency graph of the codebase:

```
DependencyGraph:
    symbol → [depends_on: Symbol]
    symbol → [depended_on_by: Symbol]
    file → [imports: File]
    file → [imported_by: File]
    module → [exposes: Symbol]
    module → [consumes: Symbol]
```

This graph is updated incrementally as events flow through the system. It powers:

- **Impact analysis**: When a symbol changes, instantly identify all affected consumers
- **Smart conflict detection**: Flag changes that break downstream dependencies even across file boundaries
- **Safe merge verification**: After a merge, verify that the dependency graph is still consistent
- **Review prioritization**: Changes that affect many downstream consumers get higher review priority

## Layer 3: Agent Workflow Layer

This layer provides primitives designed specifically for how AI agents work.

### Explorations

An exploration is the fundamental unit of agent work. It's lighter than a branch and designed for speculative, throwaway work.

```
Exploration {
    id:          UUID
    parent:      EventID (forked from this point)
    agent:       ActorID
    intent:      Intent
    status:      Active | Committed | Abandoned | Pruned
    created_at:  Timestamp
    ttl:         Duration (auto-prune after this)
    snapshot:    CoW reference to the storage engine
}
```

Key properties:

- **Near-zero creation cost**: An exploration is just a CoW snapshot pointer plus metadata. Creating one takes microseconds.
- **Isolated**: An agent's exploration doesn't affect any other timeline. Multiple agents can explore conflicting approaches simultaneously.
- **Time-limited**: Explorations have a TTL. If not committed or explicitly preserved, they auto-prune. This prevents abandoned explorations from consuming storage forever.
- **Promotable**: When an exploration produces good results, it can be promoted to a "real" branch or merged directly into main.
- **Nestable**: An exploration can fork sub-explorations. This creates a tree of speculative work that can be navigated and compared.

**Exploration lifecycle:**

```
Create → Agent works (events append to exploration timeline)
       → Agent checkpoints periodically
       → Agent evaluates result
       → Either: Promote (merge into target branch)
       → Or:     Abandon (mark for pruning)
       → Pruner garbage collects after TTL
```

### Agent Sessions

A session wraps a series of explorations by a single agent working on a single task:

```
Session {
    id:            UUID
    agent:         ActorID
    initiator:     ActorID (human who triggered this)
    task:          TaskDescription
    explorations:  [ExplorationID]
    decisions:     [Decision]
    result:        Pending | Completed(ExplorationID) | Failed(reason)
    resources:     ResourceUsage (tokens, compute time, API calls)
}

Decision {
    exploration:   ExplorationID
    action:        Kept | Discarded
    reason:        string
    confidence:    f64
}
```

Sessions provide:

- **Audit trail**: Full record of what an agent tried, what it kept, and why
- **Cost tracking**: How much compute was spent on this task
- **Reproducibility**: Given the same starting state and task, can we reproduce the agent's work
- **Learning signal**: Which exploration strategies tend to produce better results

### Workspace Isolation

Each agent operates in a virtual workspace — a lightweight, sandboxed view of the repository:

```
Workspace {
    id:          UUID
    base:        EventID (point-in-time snapshot this workspace is built from)
    overlay:     [Event] (local modifications not yet committed)
    permissions: AccessPolicy (what this workspace can read/write)
    resource_limits: ResourceLimits (max storage, max events/sec)
}
```

Workspaces are implemented using the CoW snapshot mechanism from the storage layer. The agent sees what appears to be a full copy of the repository, but only changed blocks are actually materialized. This means:

- Agents can't interfere with each other
- A runaway agent can't corrupt the main timeline
- Resource limits prevent a single agent from exhausting system resources
- The access policy limits what code an agent can even see (important for security-sensitive code)

### Checkpoint and Rollback

Agents can checkpoint at any point, creating a named snapshot they can return to:

```
checkpoint("before-refactor")
  ... agent works ...
  if not satisfied:
    rollback("before-refactor")
    ... try a different approach ...
```

This is trivial with the event log model — a checkpoint is just a labeled event, and rollback means starting a new event chain from that point. No copying, no undoing work, just forking the timeline.

### Work Queue (Built-in Task Graph)

Most VCS tools treat "what should be done" and "what was done" as completely separate systems — your tasks live in Jira or GitHub Issues, your code lives in git, and the two are loosely connected by commit messages that reference ticket numbers. For agents, this separation is fatal. An agent needs to know what to work on next, what's blocked, what just finished, and what was discovered along the way — and it needs this information to be queryable, dependency-aware, and tightly coupled to the code changes themselves.

Steve Yegge's Beads project proved this insight: agents need a structured, queryable work graph — not markdown TODO files, not external issue trackers. Beads showed that when you give agents a real dependency-aware task system with priority levels and ready-state detection, they become dramatically more effective. They can orient themselves, pick up where they left off, and discover new work without human hand-holding.

Flock absorbs this concept as a built-in subsystem. The work queue isn't a separate tool — it's part of the VCS, which means tasks are versioned, branched, and merged alongside the code they describe.

```
Task {
    id:            TaskID (hash-based, collision-resistant)
    title:         string
    description:   string
    kind:          Feature | Bugfix | Refactor | Test | Docs | Discovery
    priority:      Critical(0) | High(1) | Medium(2) | Low(3) | Backlog(4)
    status:        Open | InProgress(ActorID) | Blocked | Done | Archived
    dependencies:  [Dependency]
    linked_events: [EventID] (commits/explorations that address this task)
    discovered_by: TaskID? (if found while working on another task)
    created_at:    Timestamp
    updated_at:    Timestamp
}

Dependency {
    kind:    Blocks | ParentOf | RelatedTo | DiscoveredFrom
    target:  TaskID
}
```

**Why this belongs in the VCS, not in a separate tool:**

First, tasks and code are versioned together. When an agent creates a branch to work on Task A and discovers that it also needs Task B, both the new task and the code change are part of the same event stream. When branches merge, tasks merge. When you undo, task state undoes. There's no sync problem between "what the issue tracker says" and "what the code shows" because they're the same system.

Second, the VCS already knows things the task system needs. Flock's semantic layer can automatically detect that a commit breaks an interface used by 12 callers and create a discovery task for each affected area. The dependency graph can flag "Task B depends on code that Task A is actively modifying — these are implicitly linked." No manual tagging required.

Third, agents working in isolated workspaces need local task state. An agent can claim a task, work on it in its workspace, discover sub-tasks, and complete — all without network calls to an external service. When the workspace merges back, the task updates merge too.

**The ready queue — what should an agent work on next?**

The critical operation is `fl ready`, which answers: "given the current dependency graph, what tasks are unblocked and available to work on?"

```bash
fl ready                          # Show all unblocked tasks, sorted by priority
fl ready --agent agent-A          # Filter to tasks this agent can work on
fl ready --scope src/Services/    # Filter to tasks affecting this area
fl ready --json                   # Machine-readable output for agent consumption
```

An agent starting a new session runs `fl ready --json`, picks the highest-priority unblocked task, claims it with `fl task claim <id>`, works in its exploration, and when done runs `fl task done <id>`. If it discovers new work along the way, `fl task create --discovered-from <current-id>` links the new task back to its origin.

**Task lifecycle integrated with explorations:**

```
fl task create "Refactor payment validation" --priority 1 --kind refactor
  → Creates task tk-a1b2

fl explore start --task tk-a1b2
  → Creates exploration linked to the task
  → Task status automatically moves to InProgress

  ... agent works, discovers a bug ...

  fl task create "Fix null check in Calculate()" --kind bugfix \
    --discovered-from tk-a1b2 --priority 0
    → Creates tk-c3d4, linked back to the parent task

fl explore promote
  → Exploration merges into main
  → Task tk-a1b2 automatically moves to Done
  → tk-c3d4 is now unblocked and appears in `fl ready`
```

**Task compaction — keeping history manageable:**

Over time, completed tasks accumulate. Flock borrows Beads' concept of compaction — old completed tasks get summarized (the full detail is still in the event log history, but the active task database stays lean). This keeps the context small enough for agents to load into their context window quickly.

**What this replaces:**

For agent-driven workflows, Flock's built-in work queue replaces Jira, GitHub Issues, Beads, and scattered markdown TODO files. Everything is in one place, queryable, dependency-aware, and version-controlled. For human workflows that need richer project management (sprint planning, cross-team coordination, external stakeholder visibility), teams can still use external tools — Flock's task data can be synced outward to GitHub Issues or other systems via the event webhook system.

## Layer 4: Collaboration Layer

This layer manages multi-agent and human-agent coordination.

### Presence and Awareness

Flock tracks who is working on what in real time:

```
Presence {
    actor:       ActorID
    workspace:   WorkspaceID
    active_files: [FilePath]
    intent:      Intent (what they're trying to do)
    last_active: Timestamp
}
```

This powers:

- **Collision avoidance**: Before an agent starts working on a file, it can check if another agent is actively modifying related code
- **Coordination hints**: "Agent B is refactoring the same module you're about to touch — wait or coordinate?"
- **Dashboard visibility**: Humans can see what all agents are doing across the repository

### Change Subscriptions

Actors can subscribe to changes in specific areas of the codebase:

```
Subscription {
    actor:    ActorID
    filter:   ChangeFilter (by path, by symbol, by module, by intent category)
    notify:   NotificationConfig (immediate, batched, digest)
}
```

When a change matching a subscription's filter is committed, the subscriber is notified. This enables reactive workflows — an agent watching for changes to an API interface can automatically update documentation or client code when the interface changes.

### Human-in-the-Loop Gates

Certain operations can require human approval before proceeding:

```
Gate {
    trigger:      GateCondition
    requires:     ApprovalPolicy
    on_pending:   Block | QueueAndContinue
    timeout:      Duration
}

GateCondition:
    | FileTouched(path_pattern)
    | SymbolModified(symbol_pattern)
    | ImpactExceeds(threshold)  (changes affecting more than N downstream consumers)
    | SecuritySensitive(classification)
    | AgentConfidenceLow(threshold)
```

This lets teams define policies like "any change to the payment processing module requires human review before merge" or "if an agent's confidence in its change is below 0.8, queue for human review."

### Conflict Resolution Protocol

When true semantic conflicts occur, Flock provides a structured resolution process:

1. **Detection**: The semantic merge engine identifies the conflict and its scope
2. **Classification**: Is this a trivial formatting conflict, a logic conflict, or a breaking API change?
3. **Suggestion**: The system proposes resolution options ranked by likelihood of correctness
4. **Resolution**: A human or authorized agent selects a resolution
5. **Verification**: The dependency graph is rechecked to ensure the resolution doesn't introduce new issues
6. **Recording**: The resolution decision is recorded with full context for future learning

### Git and jj Compatibility Layer

Adoption is the hardest problem. Flock includes bidirectional compatibility with both git and jj:

- **Git import**: Convert a git repository to Flock format, preserving full history
- **jj import**: Convert a jj repository to Flock, preserving change IDs, operation history, and conflict metadata (much more natural mapping than git)
- **Git export**: Generate git-compatible history from Flock events (lossy — git can't represent explorations, intents, etc.)
- **Bridge**: A Flock repo can push/pull to a git remote, translating between formats
- **Shadow mode**: Run Flock alongside git in the same repository, using git as the "official" history and Flock as a layer on top (similar to how jj runs colocated with git today)

Shadow mode is the key adoption strategy. Teams can start using Flock explorations and semantic diff without abandoning git. Over time, as confidence builds, they can migrate fully. The jj-to-Flock migration path is especially smooth since the conceptual models are closely aligned.

## Data Model Summary

Tying it all together, here's how the core data types relate:

```
Repository
  ├── EventLog: append-only sequence of Events
  │     ├── Event → references ContentStore blocks
  │     ├── Event → may be a Checkpoint (≈ commit)
  │     ├── Event → may be tagged with Intent
  │     └── Event → may be an Undo (pointer rewind, not data deletion)
  │
  ├── ContentStore: content-addressed block storage
  │     ├── Block → raw bytes, identified by BLAKE3 hash
  │     └── FileIndex → maps (path, event) to [Block]
  │
  ├── SemanticIndex
  │     ├── AST cache per file version
  │     ├── DependencyGraph across codebase
  │     ├── SymbolTable for cross-file references
  │     └── SemanticChangeSet → high-level review summaries per checkpoint
  │
  ├── Explorations
  │     ├── Exploration → CoW snapshot + event sub-chain
  │     └── Session → groups explorations by task
  │
  ├── WorkQueue
  │     ├── Task → priority, status, dependencies, linked events
  │     ├── DependencyGraph → DAG of task relationships
  │     └── ReadyQueue → computed view of unblocked tasks by priority
  │
  ├── Collaboration
  │     ├── Presence → who's working where
  │     ├── Subscriptions → change notifications
  │     ├── Gates → approval requirements
  │     └── Locks → advisory region locks with TTL
  │
  └── Refs
        ├── Branches → named pointers to events
        ├── Tags → named pointers to checkpoints
        └── Workspaces → per-agent isolated views with auto-rebase config
```

## Implementation Strategy

### Backend Strategy: Git-Compatible First, Native Later

A critical adoption decision: should Flock use git as its storage backend (like jj does), or should it use its own native storage from day one?

The answer is both — as a two-phase strategy.

**Phase 1 backend — Git-compatible mode ("colocated"):**

In this mode, Flock stores commits as real git commits in a standard `.git/` directory, exactly like jj does today. Everything that Flock adds beyond git's model lives in a separate `.flock/` directory:

```
my-project/
  .git/           ← Standard git repository (commits, trees, blobs)
  .flock/
    event-log/    ← Fine-grained operation history
    semantic/     ← AST cache, dependency graph, symbol table
    explorations/ ← Exploration metadata and CoW snapshots
    intents/      ← Intent tags linked to commits
    config.toml   ← Flock configuration
  src/
  tests/
```

In this mode, you lose some features that require the native storage engine:

- No block-level deduplication (git stores whole files, so Flock falls back to file-level)
- Explorations are backed by git refs (works, but heavier than native CoW snapshots)
- No sub-file undo (undo operates at the commit level, like jj's `undo`)

But you gain the most important thing: **zero-risk adoption**. Your team can use Flock while the rest of the company uses git. CI/CD keeps working. GitHub/GitLab keep working. You can always `git log` and see a normal history. If Flock doesn't work out, you just delete `.flock/` and you still have a perfectly normal git repo.

This is exactly the jj playbook, and it's proven to work.

**Phase 2 backend — Native mode:**

Once a team is committed to Flock, they can migrate to the native storage engine. This unlocks block-level storage, native CoW explorations with TTLs, sub-file undo, and the full performance benefits. The git bridge still works for pushing/pulling to remotes (translating Flock events into git commits for the remote), but locally you're running on the native engine.

```
my-project/
  .flock/
    store/        ← Block-level content-addressable storage (BLAKE3)
    event-log/    ← Full event log with nanosecond precision
    merkle/       ← Snapshot Merkle trees
    semantic/     ← AST cache, dependency graph
    explorations/ ← Native CoW snapshots
    git-bridge/   ← Cached git translation layer for remote sync
    config.toml
  src/
  tests/
```

Migration from git-compatible to native mode should be a single command (`fl migrate --native`) that converts the git history into native events and builds the block-level content store.

### Build Phases

**Phase 1: Git-Compatible Backend + Core UX (MVP)**

Build the git-compatible backend, the event log (as sidecar data), CoW explorations (backed by git refs), and the core CLI. At this stage, Flock works like "jj with explorations" — a better git experience with agent-friendly primitives. Someone who knows jj should feel instantly productive.

**Deliverables**: `init`, `commit`, `push`, `pull`, `explore`, `undo`, colocated git mode

**Language**: Rust (performance-critical, single-binary distribution)

**Phase 2: Semantic Layer (C# First)**

Add the language analyzer plugin system and the first analyzer for C#. This enables AST-aware diffing and semantic merge for .NET codebases. Text fallback for everything else. Also adds the semantic code review view.

**Deliverables**: `diff --semantic`, `merge --semantic`, `review`, C# language plugin

**Dependencies**: tree-sitter C# grammar, Roslyn for deeper type analysis

**Phase 3: Agent Workflow Primitives**

Add sessions, workspaces, provenance tracking, and the gate system. This is where Flock becomes truly agent-native.

**Deliverables**: `session`, `workspace`, gate configuration, provenance queries

**Phase 4: Native Storage Engine**

Build the native backend with block-level storage, native CoW snapshots, and the migration tooling from git-compatible mode. This is the performance and efficiency phase.

**Deliverables**: Native backend, `migrate --native`, block-level dedup, sub-file undo

**Phase 5: Collaboration and Scale**

Add presence, subscriptions, coordination protocol, server-side computation for large repos, and tiered storage. This is the enterprise readiness phase.

**Deliverables**: Real-time presence, change subscriptions, region locking, tiered storage, access control

**Phase 6: Intelligence Layer**

Add the natural language query interface, AI-powered merge conflict resolution, and automatic intent extraction. This is where the system becomes truly intelligent.

**Deliverables**: `query`, smart merge suggestions, intent auto-tagging

## Technical Decisions and Trade-offs

### Why Rust for the Core

The storage engine needs to be fast, memory-safe, and distributable as a single binary. Rust gives us all three. The plugin system for language analyzers can support plugins written in any language via a well-defined FFI or gRPC interface.

### Why BLAKE3 Over SHA-1/SHA-256

BLAKE3 is significantly faster than both SHA-1 and SHA-256 (especially on modern CPUs with SIMD), produces 256-bit hashes (vs SHA-1's 160-bit), and has no known vulnerabilities. For a system doing high-frequency hashing of many small blocks, the performance difference matters.

### Why Append-Only Event Log Over Git's DAG

Git's commit DAG is elegant but optimized for human-pace development. The event log is optimized for machine-pace development. Events are cheaper to create, easier to replicate, and support richer queries. Checkpoints provide the same "clean history" view that git commits do.

The trade-off is that raw event history is noisier. But that's a feature for agent workflows — you want the full trace when debugging an agent's behavior, and you want the clean checkpoints for human review.

### Why Block-Level Over File-Level Storage

The trade-off is complexity. File-level storage (git's model) is simpler to implement and reason about. Block-level storage requires maintaining file-to-block indices and handling block boundary decisions. The payoff is dramatic storage efficiency when agents are making many small changes to large files — common in enterprise codebases with large generated files, configuration files, and complex class hierarchies.

### Why Semantic Merge is Optional

Semantic merge is powerful but fragile. It depends on correct parsing, which depends on compilable code, which agents don't always produce mid-exploration. Making the semantic layer a graceful-degradation option rather than a requirement means the system is always reliable, and gets smarter when conditions allow.

## Open Questions

Several design decisions remain open and would benefit from real-world experimentation:

**Block boundary strategy.** Fixed-size blocks are simple but produce suboptimal boundaries. Content-defined chunking (like Rabin fingerprinting) adapts to content but adds complexity. Language-aware chunking (one block per function) is ideal for code but doesn't work for non-code files. Likely answer: configurable per file type.

**Event log compaction.** The append-only log grows forever. When and how to compact? Discarding abandoned explorations is easy. Compacting committed history is harder — you need to preserve Merkle integrity while reducing event count. This is analogous to git's packfile generation but more complex.

**Multi-repo coordination.** How do explorations and semantic analysis work across repository boundaries? In a microservices world, an API change in repo A affects consumers in repos B, C, and D. The dependency graph needs to span repositories.

**Offline operation.** Git works fully offline. Flock's collaboration features (presence, subscriptions, gates) require connectivity. How much of the system works offline, and how does it reconcile when reconnecting? The event log model helps here — you can append events offline and merge event streams on reconnect.

**Performance of AST diffing at scale.** Tree edit distance is computationally expensive (O(n³) in the general case, though practical algorithms are faster on typical code). For a monorepo with thousands of files, can semantic diffing keep up with agent-pace development? May need incremental/partial approaches.
